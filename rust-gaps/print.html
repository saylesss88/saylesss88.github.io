Input and Output (I/O)

Before writing any Rust, it helps to understand what I/O actually is at the operating system level, because std::io is just a safe wrapper around these primitives.

What I/O Is

Every program that runs on your system gets three open “channels” from the OS automatically:

StreamNumberPurpose
stdin0Data coming into your program
stdout1Normal output going out
stderr2Errors and diagnostics going out

These are called file descriptors, and despite the name, they don’t have to be files. They can be your terminal, a file on disk, a network socket, or the output of another program. The OS abstracts all of that away behind a uniform interface.

The Terminal is the Default

When you run a program in your shell without doing anything special, all three streams connect to your terminal:

  • You type → that goes to stdin
  • The program prints → that goes to stdout → you see it
  • The program errors → that goes to stderr → you also see it (but separately)

This is why you can see both normal output and error messages in the same terminal window. They’re two distinct streams that just happen to both display there by default.

Redirection and Pipes

The shell lets you rewire these streams. This is where I/O becomes composable:

# Send stdout to a file instead of the terminal
echo "hello" > output.txt

# Feed a file into stdin instead of the keyboard
sort < names.txt

# Pipe stdout of one program into stdin of another
cat names.txt | sort | uniq

That last example chains three programs together. Each one reads from stdin and writes to stdout. None of them know or care what’s on the other end. This is the Unix philosophy: small programs that do one thing, composable via streams.

stderr Stays Separate

Notice that > only redirects stdout. stderr keeps going to your terminal:

# This saves stdout to a file, but errors still print to your screen
cargo build > build_output.txt

# To redirect stderr too:
cargo build > build_output.txt 2> errors.txt

# Or merge both into one file:
cargo build > all_output.txt 2>&1

This separation matters: tools that process your output (like grep or awk) read from stdout. You don’t want error messages polluting that stream.

I/O in Rust

Rust’s std::io module gives you handles to those three OS streams you just read about. The mapping is direct:

OS StreamRust
stdin (0)std::io::stdin()
stdout (1)std::io::stdout()
stderr (2)std::io::stderr()

stdin Is Not Your Command-Line Arguments

This trips up a lot of newcomers. When you run:

cargo run myfile.txt

myfile.txt does not arrive via stdin. It’s a command-line argument. A string passed to your program by the shell before it even starts. You access those through std::env::args(), which we’ll cover in the next chapter.

stdin is a stream: data that flows into your program while it’s running. That happens through pipes and redirection:

# This sends data through stdin
echo "hello" | cargo run

# So does this
cargo run < myfile.txt

# This does NOT: "myfile.txt" is an argument, not stdin
cargo run myfile.txt

A program like cat handles both: if you give it a filename as an argument it opens that file itself, but if you pipe data in it reads from stdin. That dual behavior is a common Unix convention, and you’ll implement exactly that pattern later when we get to argument parsing.

Reading from stdin

The simplest case: read a line the user types.

use std::io;
use std::io::BufRead;

fn main() {
    let stdin = io::stdin();
    let mut line = String::new();

    stdin.lock().read_line(&mut line).expect("failed to read line");

    println!("You typed: {line}");
}

A few things worth noticing:

  • stdin() returns a handle to the stdin stream
  • .lock() gives you exclusive access to it, stdin is shared across threads, so you lock it before reading
  • read_line appends into a String and includes the trailing \n. You’ll often want .trim() when you use the value
  • The BufRead trait is what provides read_line. It has to be in scope for the method to be available

Why BufRead?

Reading from a stream one byte at a time is expensive. Each read is a syscall into the OS kernel. Buffering solves this by reading a chunk at a time into memory, then serving your code from that buffer.

stdin() is already buffered by default. When you call .lock() you get a StdinLock, which implements BufRead. For files and other readers you’ll often wrap them yourself:

use std::io::{self, BufRead, BufReader};
use std::fs::File;

fn main() {
    let file = File::open("names.txt").expect("could not open file");
    let reader = BufReader::new(file);

    for line in reader.lines() {
        let line = line.expect("failed to read line");
        println!("{line}");
    }
}

The same BufRead trait works whether you’re reading from stdin, a file, or anything else that implements Read. That’s the point, your code doesn’t need to care what’s on the other end.

Writing to stdout and stderr

println! and eprintln! cover most cases, but you can also write to the handles directly:

use std::io::{self, Write};

fn main() {
    let mut stdout = io::stdout();
    let mut stderr = io::stderr();

    writeln!(stdout, "this goes to stdout").unwrap();
    writeln!(stderr, "this goes to stderr").unwrap();
}

One gotcha with stdout: it’s line-buffered by default when connected to a terminal. Output is flushed when a newline is written. If you need output to appear immediately without a newline. Like a prompt, you have to flush manually:

use std::io::{self, Write};

fn main() {
    print!("Enter your name: ");
    io::stdout().flush().unwrap();

    let mut name = String::new();
    io::stdin().lock().read_line(&mut name).unwrap();
    println!("Hello, {}!", name.trim());
}

Without the flush() call the prompt might not appear before the program blocks waiting for input.

Reading All of stdin

When your program is used in a pipe, you often want to process everything coming in rather than one line at a time:

use std::io::{self, Read};

fn main() {
    let mut input = String::new();
    io::stdin().lock().read_to_string(&mut input).unwrap();

    println!("Got {} bytes", input.len());
}

You can test this directly from the shell:

echo "hello world" | cargo run

This is the pattern most Unix-style Rust tools are built on. Read from stdin, write to stdout, report errors to stderr.

Command-Line Arguments std::io::args()

As we covered, stdin is the stream, data flowing into your program through pipes. Command-line arguments are different: they’re strings the shell hands to your program at startup, before it runs a single line of code.

When you type:

cargo run -- hello world

The OS passes [“hello”, “world”] to your program as a list of strings. Rust exposes these through std::env::args().

The Basics

use std::env;

fn main() {
    let args: Vec<String> = env::args().collect();
    println!("{args:?}");
}

Run it:

cargo run -- hello world

Output:

["target/debug/myprogram", "hello", "world"]

☝️

This is the argument vector: argv in C terminology. The name comes from C’s main(int argc, char *argv[]), where argc is the count and argv is the array of argument strings. Rust inherits this convention: the binary path is always first, your arguments follow. You’ll see argv referenced in shell docs and system programming literature, so it’s worth knowing the term.

The first element as stated above, is always the binary itself. Your actual arguments start at index 1. This is a Unix convention inherited from C.

args() Returns an Iterator

env::args() doesn’t return a Vec, it returns an iterator. Calling collect() is what pulls it into a Vec. You can also work with it directly:

use std::env;

fn main() {
    for arg in env::args().skip(1) {
        println!("{arg}");
    }
}

.skip(1) drops the binary name so you’re only iterating your actual arguments. This is a common pattern.

Accessing Specific Arguments

use std::env;

fn main() {
    let args: Vec<String> = env::args().collect();

    if args.len() < 2 {
        eprintln!("usage: {} <name>", args[0]);
        std::process::exit(1);
    }

    let name = &args[1];
    println!("Hello, {name}!");
}

A few things to notice:

  • Error messages go to stderr via eprintln!; tools that consume your stdout won’t get garbage mixed in
  • args[0] in the usage message is a nice touch, it automatically uses whatever the binary is named
  • std::process::exit(1) signals failure to the shell; 0 means success, anything else means failure
  • env::args() panics if any argument contains invalid UTF-8. In those cases, use env::args_os() instead, which returns OsString rather than String.

Where This Leads

Accessing args() directly works fine for simple tools, but once you have more than two or three arguments you’ll want structure: named flags, optional values, help text. That’s where argument parsing crates come in, clap being the most common. We’ll cover that in a later chapter.

For now the mental model is: stdin is the stream, args are the words after the command, and env::args() is how Rust hands you those words.

Decoding the map Signature

#![allow(unused)]
fn main() {
pub fn map<U, F>(self, f: F) -> Option<U>
where
    F: FnOnce(T) -> U,
}
  • self (by value): It takes ownership of the Option<T>. Because it consumes it, you can’t use the original Option afterward, it gets transformed into the new one.
  • f: F where F: FnOnce(T) -> U: It takes any closure or function that accepts T (the inner value) and spits out a U. FnOnce is the most permissive closure trait; it just means “you only need to be able to call this once”.
  • -> Option<U>: Generic type parameters (T and U) are independent, not distinct. U can be a different type (like turning Option<i32> into Option<String>), or U can resolve to the same type as T.

Naive map Implementation without Generics

#![allow(unused)]
fn main() {
#[derive(Debug, PartialEq)]
pub enum IntOption {
    Some(i32),
    None,
}

impl IntOption {
    // Takes `self` by value (consumes it) and a function `f`
    pub fn map<F>(self, f: F) -> IntOption
    where
        F: FnOnce(i32) -> i32,
    {
        match self {
            IntOption::Some(x) => IntOption::Some(f(x)),
            IntOption::None => IntOption::None,
        }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn maps_same_type() {
        let num = IntOption::Some(10);
        let doubled = num.map(|x| x * 2);
        assert_eq!(doubled, IntOption::Some(20));
    }

    #[test]
    fn maps_none_without_running_closure() {
        let empty = IntOption::None;
        let result = empty.map(|_| panic!("This should never execute"));
        assert_eq!(result, IntOption::None);
    }
}
}

Notice how f is just a variable holding a function or closure. In the Some(x) arm, you call f(x) and wrap the result back into IntOption::Some(...). In the None arm, f is never called and gets dropped when the method exits.

The Generic Version (T to U)

#![allow(unused)]
fn main() {
#[derive(Debug, PartialEq)]
pub enum MyOption<T> {
    Some(T),
    None,
}

impl<T> MyOption<T> {
    // `<U, F>` introduces two new generic types local to this method:
    // U = whatever type the closure returns
    // F = the specific closure type being passed in
    pub fn map<U, F>(self, f: F) -> MyOption<U>
    where
        F: FnOnce(T) -> U,
    {
        match self {
            MyOption::Some(val) => MyOption::Some(f(val)),
            MyOption::None => MyOption::None,
        }
    }
}
}
  • The first <T> (after impl) declares that T is a generic type parameter, not a concrete struct named T.
  • The second <T> (after MyOption) uses that parameter to specify which type you are implementing methods for.

Verify with Unit Tests

Add a tests module at the bottom of src/lib.rs and run cargo test.

#![allow(unused)]
fn main() {
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn maps_same_type() {
        let num = MyOption::Some(10);
        let doubled = num.map(|x| x * 2);
        assert_eq!(doubled, MyOption::Some(20));
    }

    #[test]
    fn maps_different_type() {
        let num = MyOption::Some(42);
        // Here T is i32, and U becomes String
        let text = num.map(|x| format!("Answer: {x}"));
        assert_eq!(text, MyOption::Some(String::from("Answer: 42")));
    }

    #[test]
    fn maps_none_without_running_closure() {
        let empty: MyOption<i32> = MyOption::None;
        let result = empty.map(|_| panic!("This should never execute"));
        assert_eq!(result, MyOption::None);
    }
}
}

Clap Derive

Understanding clap by Building It Yourself

Most tutorials start with clap and show you how to use it. This one starts without it.

Before reaching for clap, it’s worth building the same thing by hand. Parsing arguments manually forces you to see exactly what clap is doing for you, and once you see that, the derive API stops feeling like magic and starts feeling obvious.

We’ll build echor (Credit: Command-Line Rust), a Rust implementation of the Unix echo command in three passes:

  1. Raw args: env::args() directly in main, no abstractions
  2. Structured args: a typed struct with a build method, same shape clap uses
  3. clap derive: replace build() with #[derive(Parser)] and watch how little changes

Then we’ll close by looking at what clap is actually doing internally, by implementing a naive version of its three-trait pipeline.

What problem does clap solve?

When a user runs your program, the OS hands it a flat list of strings:

cargo run -- hello world -n
# the program receives: ["target/debug/echor", "hello", "world", "-n"]

Your program has to:

  1. Parse: decode what each string means (is -n a flag? is hello positional text?)
  2. Validate: check the result makes sense (did the user provide any text at all?)
  3. Run: use the validated result

clap handles steps one and two automatically. By the time your main logic runs, you’re guaranteed a valid, typed Args struct. That guarantee, and the help text, error messages, and type coercion you get for free. (is the entire value proposition).

Pass 1: Raw args in main

echo takes literal text arguments and an optional -n flag to suppress the trailing newline. Let’s implement it with nothing but the standard library:

use std::env;

fn main() {
    let args: Vec<String> = env::args().collect();

    let mut omit_newline = false;
    let mut text: Vec<String> = Vec::new();

    // parsing: decide where each arg goes
    for arg in args.iter().skip(1) {
        if arg == "-n" {
            omit_newline = true;
        } else {
            text.push(arg.clone());
        }
    }

    // validation: checks that the result is usable
    if text.is_empty() {
        eprintln!("error: at least one argument required");
        std::process::exit(1);
    }

    // logic: use the validated result
    print!("{}{}", text.join(" "), if omit_newline { "" } else { "\n" });
}

Walking through the pieces:

  • env::args().collect() gives you every string the OS passed in, including args[0] which is always the binary path, not user input
  • .skip(1) drops that binary name so the loop only sees actual arguments
  • omit_newline is a bool because -n is either present or not
  • text is a Vec<String> because echo can take multiple words. Every non-flag arg gets pushed in
  • text.join(" ") collapses the vec back into a single string: ["hello", "world"] → “hello world”
cargo run -- hello world
# args[0] = "target/debug/echor"  (skipped)
# args[1] = "hello"               → text
# args[2] = "world"               → text
# Output: hello world

This works, but everything lives in main: the parsing variables, the loop, the validation, and the output logic are all tangled together. That three-phase structure: parse, validate, run is implicit. The next pass makes it explicit.

Pass 2: Typed struct with build()

The same logic, reorganized around a struct:

use std::{env, error::Error};
type Result<T> = std::result::Result<T, Box<dyn Error>>;

const USAGE: &str = "\
      Usage: echors [OPTIONS] <TEXT>...
      Arguments:\n <TEXT>... Input text
      Options:\n
      -V, --version       Print version
      -h, --help          Print help
      -n                  Do not print newline
";

#[derive(Debug)]
struct Args {
    /// The text values to be printed to standard output
    text: Vec<String>,
    /// Flag indicating whether the trailing newline (`\n`) should be omitted
    omit_newline: bool,
}

impl Args {
    /// Parses and validates cli arguments manually from `env::args()`
    ///
    /// # Errors
    /// Returns a string slice error message if no text arguments are provided
    fn build() -> Result<Args> {
        let mut args = Args {
            text: Vec::new(),
            omit_newline: false,
        };

        // Skip the first argument (the binary path) & iterate through user inputs
        for arg in env::args().skip(1) {
            if arg == "-n" {
                args.omit_newline = true;
            } else if arg == "-h" || arg == "--help" {
                println!("{USAGE}");
                process::exit(0)
            } else if arg == "-V" || arg == "-version" {
                println!("echors {}", env!("CARGO_PKG_VERSION"));
                process::exit(0)
            } else {
                args.text.push(arg);
            }
        }
        // Validate that required arguments are present
        if args.text.is_empty() {
            eprintln!("{USAGE}");
            return Err("at least one argument required".into());
        }
        Ok(args)
    }
}

fn main() -> Result<()> {
    // Parse arguments and handle validation errors
    let args = Args::build()?;
    // Print the joined text, appending a newline unless `-n` was specified
    print!(
        "{}{}",
        args.text.join(" "),
        if args.omit_newline { "" } else { "\n" }
    );
    Ok(())
}

The code does basically the same thing as Pass 1. What changed is the structure:

  • Args is now a type. The shape of valid input is declared once and reused everywhere. In Pass 1, omit_newline and text were local variables that only existed inside main. Here they’re fields on a struct, which means the compiler can check that you’re using them correctly, and any function that receives an Args knows exactly what it’s working with.
  • build() owns the parse-and-validate phase. It returns Result<Args>, so errors are values your program can handle rather than panics or process::exit calls scattered through main. By the time build() returns Ok, the args are guaranteed valid, the same guarantee clap provides.
  • main is reduced to three lines. Call build(), propagate any error with ?, run the logic. The three phases: (parse, validate, and run) are now enforced by the structure of the code rather than just implied by comments.

This is exactly the shape clap’s derive API generates for you. In Pass 3, build() disappears and #[derive(Parser)] takes its place. But Args, main, and the Result-based error flow stay identical.

Pass 3: clap derive

Now replace build with #[derive(Parser)]:

use clap::Parser;

/// Rust version of `echo`
#[derive(Debug, Parser)]
#[command(author, version, about)]
struct Args {
    /// Input text
    text: Vec<String>,

    /// Do not print newline
    #[arg(short('n'))]
    omit_newline: bool,
}

fn main() {
    let args = Args::parse();

    print!(
        "{}{}",
        args.text.join(" "),
        if args.omit_newline { "" } else { "\n" }
    );
}

IMO, Pass 2 is arguably more clear as to what is going on. This version is shorter and easier to write.

Note

Notice that main now receives a clean Args value with no Option or Result to unwrap. This is the pattern clap enforces: by the time you reach your logic, parsing and validation are already done.

The struct is identical. main is very similar, besides the above note. The only things that disappeared are build() and the error propagation, clap handles both. What you get in exchange:

  • Automatic --help and --version flags
  • Typed error messages with usage hints when the user passes bad input
  • Type coercion ("42" → u32, paths validated as PathBuf, etc.)
  • Short and long flag variants for free (-n / --omit-newline)

The mapping from struct fields to argument types is direct:

Field typeWhat clap expects
Stringexactly one positional value
Vec<String>one or more positional values, collected
boola flag, present = true, absent = false
Option<String>one optional value, absent = None
Option<PathBuf>one optional path, absent = None
u8 with ArgAction::Counthow many times the flag was passed

The #[arg(...)] attributes are overrides on top of those defaults. Without #[arg(short('n'))], clap would infer the flag name from the field name (--omit-newline). The attribute pins it to -n.

Command-Line Argument Types

Before going further, it’s worth naming the categories clap works with, because the derive attributes map directly to them.

  • clap CLI concepts

Positional arguments: identified by their position, not a name. Order matters.

cp source.txt dest.txt
#   ^^^^^^^^^^ ^^^^^^^^
#   position 1  position 2

Flags: boolean switches, either present or not. Order doesn’t matter.

echo -n hello
ls -l
ls --long    # same as -l, long form

Short flags use a single dash and one character -n. Long flags use double dash and a word --number. They’re typically the same flag, just two ways to write it.

Options: like flags but take a value after them:

cargo run --example myexample
#          ^^^^^^^^ ^^^^^^^^^
#           option     value
cut -d "," -f 1
#      ^^^    ^
#      value  value

Subcommands: a word that selects a mode, then has its own args:

cargo build --release
#     ^^^^^
jj desc -m "message"
#  ^^^^^^

In a clap struct the field type and attributes map directly to these categories:

Arg typeClap representation
Positionalfield with no short/long, e.g. text: Vec<String>
Flagbool field with short/long
OptionOption<T> field with short/long
Subcommand#[command(subcommand)] enum field

What clap is actually doing: a naive implementation

  • clap/clap_builder/src/derive.rs

clap’s derive macro generates implementations of three traits. Here’s what each one does, translated into plain code without the macro:

use std::env;

#[derive(Debug)]
struct Args {
    text: Vec<String>,
    omit_newline: bool,
}

impl Args {
    // equivalent of CommandFactory::command()
    // collects raw argv, skipping the binary name
    // In real clap this builds a Command schema first,
    // then parses argv against it, producing ArgMatches.
    // Here we skip the schema and return raw strings directly.
    fn command() -> Vec<String> {
        env::args().skip(1).collect()
    }

    // FromArgMatches::from_arg_matches_mut()
    // Takes the parsed input and maps it onto struct fields.
    // In real clap the input is an ArgMatches (typed map of name → value).
    // Here we're working directly with raw strings.
    fn from_matches(raw: Vec<String>) -> Result<Self, String> {
        let mut text = Vec::new();
        let mut omit_newline = false;

        for arg in raw {
            if arg == "-n" {
                omit_newline = true;
            } else if arg.starts_with('-') {
                return Err(format!("unknown flag: {}", arg));
            } else {
                text.push(arg);
            }
        }

        // validation
        if text.is_empty() {
            return Err("error: at least one argument required".to_string());
        }

        Ok(Args { text, omit_newline })
    }

    // Parser::parse()
    // orchestrates the pipeline and handles errors
    fn parse() -> Self {
        let raw = Self::command();
        match Self::from_matches(raw) {
            Ok(args) => args,
            Err(e) => {
                eprintln!("{e}");
                std::process::exit(1);
            }
        }
    }
}

fn main() {
    let args = Args::parse();
    print!(
        "{}{}",
        args.text.join(" "),
        if args.omit_newline { "" } else { "\n" }
    );
}

[!NOTE] argv is short for argument vector

Real clap’s pipeline has one more step our version compresses out:

argv
  → CommandFactory::command()     builds a schema, parses argv into ArgMatches
  → ArgMatches                    a generic typed map of name → value
  → FromArgMatches::from_arg_matches_mut()   maps ArgMatches onto your struct
  → Args

Ours goes straight from raw strings to Args, skipping ArgMatches. The reason clap separates these is flexibility, you can use ArgMatches directly without a struct if you want, or implement FromArgMatches on your own type. The derive macro just generates all three trait implementations from your struct definition.

The traits clap splits this across:

  • CommandFactory: builds the Command schema
  • FromArgMatches: converts ArgMatches into your struct
  • Parser: orchestrates both and handles errors

Structs vs enums: choosing the right shape

Use a struct when your program has one mode and all arguments apply to every run (echo, cat, ls).

Use an enum when your program has multiple modes with different arguments per mode:

#[derive(Parser)]
struct Cli {
    #[command(subcommand)]
    command: Option<Commands>,
}

#[derive(Subcommand)]
enum Commands {
    /// Add a file
    Add { path: PathBuf },
    /// Remove a file
    Remove { path: PathBuf, #[arg(short)] force: bool },
    /// List files
    List,
}

Add, Remove, and List each have different arguments. You can’t represent this cleanly in a flat struct because a struct implies all fields exist for every invocation. An enum variant is exclusive: only one runs at a time.

Then in main you match on it:

match cli.command {
    Commands::Add { path } => { ... }
    Commands::Remove { path, force } => { ... }
    Commands::List => { ... }
}

Most real tools combine both. A top-level struct for global flags (like --verbose, --config) with an enum field inside it for the subcommand, exactly like the example above.

The Filesystem in Rust

Before touching std::fs, it helps to understand what the filesystem actually is from the OS’s perspective, because the module is just a safe wrapper around those primitives.

What the Filesystem Is

Your OS maintains a tree of named locations. At the root is / on Unix, C:\ on Windows. Everything else: files, directories, symlinks, and device nodes hang off that tree. The OS is the gatekeeper: your program never touches a disk directly. It asks the kernel, and the kernel decides whether to allow it.

That has two practical consequences:

  • Every filesystem operation can fail. The file might not exist, you might lack permission, the disk might be full, or a symlink might point nowhere. This is why every std::fs function returns a Result.
  • Paths are just strings the kernel interprets. They don’t have to point to anything real until you actually use them.

Paths: Path and PathBuf

Before you can do anything with the filesystem, you need to talk about paths. Rust gives you two types:

TypeAnalogous toOwned?
PathstrNo, a borrowed view
PathBufStringYes, owns the data

The same owned/borrowed pattern you already know from strings applies here. You’ll typically accept &Path in functions and build owned PathBuf values when you need to construct or store a path:

#![allow(unused)]
fn main() {
use std::path::{Path, PathBuf};

let borrowed: &Path = Path::new("theme/draw.js");

let mut owned = PathBuf::from("theme"); owned.push("draw.js"); // theme/draw.js
}

.push() is the idiomatic way to build paths, never concatenate path strings with + or format!. The OS path separator differs between platforms and you’ll get it wrong. .push() handles it correctly everywhere.

.join()`` does the same thing but returns a new PathBuf` instead of mutating in place:

#![allow(unused)]
fn main() {
let theme = Path::new("theme"); let js_path = theme.join("draw.js"); //
PathBuf: theme/draw.js
}

Checking What Exists

Before creating or modifying something, you often need to know if it’s already there:

#![allow(unused)]
fn main() {
use std::path::Path;

let dir = Path::new("theme");

if !dir.exists() { std::fs::create_dir(dir).expect("failed to create theme/"); }
}

A few things to know about .exists():

It follows symlinks; if a symlink points nowhere, .exists() returns false There’s a TOCTOU race: the path could be created or deleted between your check and your action. For most CLI tooling this doesn’t matter, but it’s worth knowing

Related methods on Path you’ll use constantly:

#![allow(unused)]
fn main() {
path.is_file()   // true if it exists and is a regular file
path.is_dir()    // true if it exists and is a directory
path.extension() // Option<&OsStr> the part after the last dot
path.file_name() // Option<&OsStr> the last component
path.parent()    // Option<&Path> everything except the last component
}

create_dir is strict, it fails if the directory already exists or if an intermediate directory is missing. create_dir_all is the mkdir -p equivalent. For init-style tooling you almost always want create_dir_all. For cases where you need to know you’re creating something fresh, create_dir gives you more control.

Error handling basics

Library crates

  • Library crates should return typed errors (usually built with thiserror). Callers need to match on them to decide what to do.

Binary crates

  • Binaries and CLI tools can use anyhow (or color-eyre) and stop there. Usually nobody matches on the error. It gets printed with context and the program exits.

Mixed crates (lib + bin)

  • Use typed errors in the lib and anyhow in main.rs.

Single error.rs vs. one error enum per module

The problem with one giant crate-wide enum is that every function returns the full set of variants, even ones it can never produce.

The fix is to scope errors to a unit of failure: a module, or even a single operation (ParseError, FetchError). A higher-level error can wrap the lower ones:

#![allow(unused)]
fn main() {
#[derive(Debug, thiserror::Error)]
pub enum ReleaseError {
    #[error("failed to parse commit log")]
    Parse(#[from] ParseError),
    #[error("failed to write changelog to {path}")]
    Write { path: PathBuf, #[source] source: io::Error },
}
}

For a small crate, one error.rs is fine. Split it up once the variants clearly divide into groups that never overlap.

Writing your own Error type

#[non_exhaustive] // callers outside this crate must include a `_ =>` arm
#[derive(Debug)]
pub enum AppError {
    Io(std::io::Error),
    ParseInt(std::num::ParseIntError),
    Custom(String),
}

#[non_exhaustive]: lets you add variants later without a breaking change. Outside your crate, exhaustive matches won’t compile; callers must handle _ =>. Inside your own crate, nothing changes. Use it when you expect the error set to grow.

We’re wrapping foreign error types as variants, plus leaving room for our own messages.

Implement Display 🤘

use std::fmt;

#[non_exhaustive]
#[derive(Debug)]
pub enum AppError {
    Io(std::io::Error),
    ParseInt(std::num::ParseIntError),
    Custom(String),
}

impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            AppError::Io(e)       => write!(f, "IO error: {e}"),
            AppError::ParseInt(e) => write!(f, "Parse error: {e}"),
            AppError::Custom(msg) => write!(f, "{msg}"),
        }
    }
}

Implement std::error::Error

#[non_exhaustive]
#[derive(Debug)]
pub enum AppError {
    Io(std::io::Error),
    ParseInt(std::num::ParseIntError),
    Custom(String),
}

impl std::error::Error for AppError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            AppError::Io(e)       => Some(e),
            AppError::ParseInt(e) => Some(e),
            AppError::Custom(_)   => None,
        }
    }
}

source() exposes the underlying cause for error chain inspection. It’s optional: the trait has a default impl that returns None, but you should implement it when you’re wrapping another error. Tools and libraries use it to walk the cause chain.

  • In the Io arm, e is a &std::io::Error.
  • Returning it as &dyn Error is an unsizing coercion. The compiler wraps the reference in a fat pointer: one half points to the data, the other to a vtable of io::Error’s Error trait methods.

Option means “is there an underlying cause?”:

  • Some(e): this error was caused by another error, and here it is.
  • None: this is the root of the chain. Custom(String) has no cause. It’s just a message you made up.

The 'static bound means the underlying error type holds no borrowed references. That’s what makes downcast_ref possible, so a caller can recover the concrete type if they really want it:

#![allow(unused)]
fn main() {
if let Some(io_err) = err.source().and_then(|e| e.downcast_ref::<std::io::Error>()) {
    // it's an io::Error again
}
}

Because each error can point to the next one, reporters like anyhow can walk the whole chain:

#![allow(unused)]
fn main() {
let mut cur: Option<&dyn Error> = Some(&err);
while let Some(e) = cur {
    eprintln!("{e}");
    cur = e.source();
}
}

That loop is what produces the “Caused by:” lines you saw earlier.

One side note: Custom(String) works, but it’s a stringly-typed escape hatch. Callers can’t match on what went wrong, only read the text. That’s fine in an app. In a library, a named variant is better.

Implement From for each wrapped type

impl From<std::io::Error> for AppError {
    fn from(e: std::io::Error) -> Self {
        AppError::Io(e)
    }
}

impl From<std::num::ParseIntError> for AppError {
    fn from(e: std::num::ParseIntError) -> Self {
        AppError::ParseInt(e)
    }
}

From is what makes the ? operator work. When you write some_io_op()?, the ? desugars to roughly:

match result {
    Ok(v) => v,
    Err(e) => return Err(AppError::from(e)),
}

So without From, ? can’t convert the foreign error into your type and you’d have to .map_err() everywhere manually.

Using It

fn read_and_parse(path: &str) -> Result<i32, AppError> {
    let content = std::fs::read_to_string(path)?;  // io::Error -> AppError via From
    let n = content.trim().parse::<i32>()?;         // ParseIntError -> AppError via From
    Ok(n)
}

fn main() {
    match read_and_parse("number.txt") {
        Ok(n)  => println!("Got: {n}"),
        Err(e) => eprintln!("Error: {e}"),
    }
}

Adding Context to Your Errors

For the Custom variant you’d typically add a constructor or just build it inline:

impl AppError {
    pub fn custom(msg: impl Into<String>) -> Self {
        AppError::Custom(msg.into())
    }
}

// usage
return Err(AppError::custom("file was empty"));

What’s the Point if they all resolve to std::error::Error types

A function can only have one return type.

fn read_and_parse(path: &str) -> Result<i32, ???> {
    let content = std::fs::read_to_string(path)?;  // io::Error
    let n = content.trim().parse::<i32>()?;         // ParseIntError
    Ok(n)
}

The two ? calls produce different error types. You can’t put two types in that slot. Your options are:

  1. Box it. Box<dyn Error>
fn read_and_parse(path: &str) -> Result<i32, Box<dyn std::error::Error>> {
    let content = std::fs::read_to_string(path)?;
    let n = content.trim().parse::<i32>()?;
    Ok(n)
}

This works, and ? handles the conversion automatically. But the caller gets a black box, they can’t match on what actually went wrong without downcasting. You’ve thrown away the type information.

  1. Your own enum, keeps the type information
fn read_and_parse(path: &str) -> Result<i32, AppError> {
    let content = std::fs::read_to_string(path)?;
    let n = content.trim().parse::<i32>()?;
    Ok(n)
}

Now the caller can actually branch on what happened:

match read_and_parse("file.txt") {
    Ok(n) => println!("{n}"),
    Err(AppError::Io(e))       => eprintln!("couldn't read file: {e}"),
    Err(AppError::ParseInt(_)) => eprintln!("file didn't contain a number"),
    Err(AppError::Custom(msg)) => eprintln!("logic error: {msg}"),
}

With Box<dyn Error> that match is impossible without ugly downcasting.

A custom enum lets a function fail in multiple distinct ways while giving callers exhaustive, typed, matchable error handling. Box<dyn Error> trades that away for convenience.

Error handling methods

.map_err()

.map_err changes the error inside a Result and leaves a success value untouched.

#![allow(unused)]
fn main() {
pub fn map_err<F, O>(self, op: O) -> Result<T, F>
where
    O: FnOnce(E) -> F,
}
#![allow(unused)]
fn main() {
fn stringify(x: u32) -> String { format!("error code: {x}") }

let x: Result<u32, u32> = Ok(2);
assert_eq!(x.map_err(stringify), Ok(2));

let x: Result<u32, u32> = Err(13);
assert_eq!(x.map_err(stringify), Err("error code: 13".to_string()));
}

Maps a Result<T, E> to Result<T, F> by applying a function to a contained Err value, leaving an Ok value untouched.

  • If it’s Ok(value), nothing happens. The closure never runs.
  • If it’s Err(e), the closure gets e and whatever it returns becomes the new error.

It’s the mirror of .map(), which changes the Ok value and leaves errors alone.

These two are equivalent:

#![allow(unused)]
fn main() {
let r = some_result.map_err(|e| convert(e));

let r = match some_result {
    Ok(v) => Ok(v),
    Err(e) => Err(convert(e)),
}
}

Examples

  1. Wrapping your error type
#![allow(unused)]
fn main() {
fn read_file(path: &str) -> Result<String, AppError> {
    std::fs::read_to_string(path).map_err(|e| AppError::Io(e))
}
}

read_to_string returns Result<String, io::Error>, but the function promises AppError, .map_err bridges the gap.

A tuple variant like AppError::Io is already a function that takes an io::Error and returns an AppError. So you can pass it directly without writing a closure:

#![allow(unused)]
fn main() {
std::fs::read_to_string(path).map_err(AppError::Io)
}
  1. Combining it with ?
#![allow(unused)]
fn main() {
fn parse_port(s: &str) -> Result<u16, AppError> {
    let port = s.trim().parse::<u16>().map_err(AppError::ParseInt)?;
    Ok(port)
}
}

Read it left to right: try to parse; if that fails, turn the error into an AppError; then ? returns early. On success, port is just a u16.

  1. Adding context
#![allow(unused)]
fn main() {
let text = fs::read_to_string(path).map_err(|source| ConfigError::Read {
    path: path.to_owned(),
    source,
})?;
}

.unwrap_or_else()

  • Option::unwrap_or_else

Returns the contained Some value or computes it from a closure.

.unwrap_or_else handles the error right there rather than passing it up.

  • .map_err keeps you inside the Result. The error is changed, then passed up with ?. The caller deals with it.

  • .unwrap_or_else gets you out of the Result. On Ok(v) you get v. On Err(e) the closure runs and must return a fallback value of the same type T. Either way you end up with a plain value, not a Result.

#![allow(unused)]
fn main() {
pub fn unwrap_or_else<F>(self, op: F) -> T
where
    F: FnOnce(E) -> T,
}

Examples

#![allow(unused)]
fn main() {
let k = 10;
assert_eq!(Some(4).unwrap_or_else(|| 2 * k), 4);
assert_eq!(None.unwrap_or_else(|| 2 * k), 20);
}
  1. Fall back to a default
#![allow(unused)]
fn main() {
let port: u16 = env::var("PORT")
    .ok()
    .and_then(|s| s.parse().ok())
    .unwrap_or_else(|| 8080);
}

That chain ends on an Option, so this closure takes no argument. On a Result, the closure receives the error.

  1. Log the error and carry on
#![allow(unused)]
fn main() {
let config = load_config(&path).unwrap_or_else(|e| {
    eprintln!("warning: {e}, using defaults");
    Config::default()
});
}
